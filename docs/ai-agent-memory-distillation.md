# AI Agent记忆库防臃肿：热冷分层蒸馏的工程实践

> 你的AI助手知识库是不是越喂越大、越来越慢？本文是一套生产环境跑了3个月的真实工程方案。

## 问题：上下文膨胀是"慢性税"

给Agent（Claude/自定义Agent）配知识库的常见路径：文档越写越多，全部塞进系统提示词。后果：

1. **每轮对话都在交"注入税"**——无论本轮任务用不用得到，几万token先烧掉
2. **注意力被占满**——驱动力/规则占比越大，留给实际推理的空间越小
3. **过期内容毒化判断**——写了3个月的旧状态（"当前X还没做"）混在新任务里，AI分不清哪些是实况

一句话：**文档库的膨胀速度，就是智能衰减的速度。**

## 方案：热冷分层（不是删除，是搬家）

核心原则：**内容永不删除，只改住址。**

```
全库文档
  ├── 热区（每会话必看）→ 主文件保留正文
  │     · 启动协议 / 核心价值观 / 高频条款
  ├── 温区（每周看一次）→ 骨架索引 + rg关键词定位
  │     · 一行标题 + "详情见分卷X" 
  └── 冷区（遇需才查）→ 分卷全文存档
        · 历史批次记录 / 完整案例 / 大表格
```

### 判定标准（三问）

每条内容问三个问题，决定它住哪：

1. **这内容最近7天被用到几次？** >3次=热区
2. **它过期了吗？** 带日期的状态描述（"当前进度X"）= 必须校准或转历史档
3. **AI需要"记住"还是"能查到"？** 能查到就够的=冷区

第三问是关键：**机器可查不等于机器要背。**

## 工程细节：三个机制

### 1. 截断探针——把"被截断"变成可测数据

在长文档的固定深度埋5个标记（10%/30%/50%/70%/95%处），每次会话开头自查"看得到/看不到"：

```
看不到的最低深度 = 截断线位置
全看到 = 全量注入
```

这把"我感觉上下文被截断了"变成一行可报警的数据：`截断线:50%`。超过阈值自动触发蒸馏，而不是等出事故。

### 2. 统一搜索器——替代全量注入的检索层

```python
# 一个入口查所有分卷
python3 统一搜索器.py "备份制度" --scope=分卷
```

关键词命中分卷文件→按需Read。知识库从"全部背下来"变成"知道去哪查"。检索精度靠标题规范保证：每条内容有唯一定位关键词，rg一下就达。

### 3. 追加式台账——防覆盖篡改

蒸馏过程本身也要可审计：每轮蒸馏后，旧版本逐字归档+新版本落盘，用jsonl追加制存哈希史。**瘦身不等于丢内容，丢没丢内容可验证。**

## 验收指标（防自我感动）

蒸馏不是"感觉清爽了"，看三个硬数：

| 指标 | 判定 |
|------|------|
| 启动注入token数 | 蒸馏前后实测对比，下降才作数 |
| grep验活 | 抽10个冷区关键词，全部rg命中=没丢内容 |
| 任务完成率 | 蒸馏后一周同类任务不返工 |

## 效果实测

一个709KB的宪法级文档，三轮蒸馏后：
- 启动注入从"必然截断"降到"全量可见"
- 冷区内容100%可rg命中（保真度不丢）
- 会话响应速度明显改善（注意力不再被历史内容稀释）
